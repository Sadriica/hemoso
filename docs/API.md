# API contract for the frontend

This is the contract Juli (Eng 2) builds the frontend against. It is written
from the code in `backend/app/`, not from memory. The machine-readable schema is
`docs/openapi.json`, generated by `backend/scripts/export_openapi.py` (regenerate
it with `uv run python scripts/export_openapi.py` from `backend/`). The field
meanings come from `../FORMATS.md`. All data is synthetic (REQ-14); nothing here
holds real personal data.

The frontend reads the base URL from a `VITE_API_BASE_URL` placeholder, never a hard-coded
host. The examples below use `$VITE_API_BASE_URL` (shell) and `VITE_API_BASE_URL` (JavaScript).

## Routes

### GET /health

Health check. No request body.

Responses: `200`.

```bash
curl "$VITE_API_BASE_URL/health"
# {"status":"ok"}
```

```js
const response = await fetch(`${VITE_API_BASE_URL}/health`);
const body = await response.json(); // { status: "ok" }
```

### POST /accounts

Creates one account (REQ-37). An account is what makes a person's data private:
once the person has one, every route that names that person needs a token (see
"Sessions and the Authorization header" below).

Request body:

| Field | Type | Rule |
| --- | --- | --- |
| `person_id` | string | at most 64 characters, lowercase `snake_case`, the same rule as everywhere else |
| `pin` | string | 4 to 8 digits, nothing else |
| `mission_start` | string, optional | the date Flight Day 1 is counted from: `YYYY-MM-DD`, a real calendar date, from `2000-01-01` up to tomorrow in UTC. Left out, the account starts without a date and `PUT /people/{person_id}/mission_start` sets it later |

What the backend stores, and nothing more: `person_id`, a random 16-byte salt
(hex), the `hashlib.scrypt` digest of the PIN with that salt (`n` = 2**14,
`r` = 8, `p` = 1), hex, and `mission_start` when the body carried one. The PIN
itself is never stored, never logged and never returned. Two accounts with the
same PIN get different hashes, because each has its own salt.

Responses: `201` with `{"person_id": "..."}`; `409` when the name is taken
(`detail` `this username is taken` for `smoke_test_1`, for any `person_id` of
`config/data/demo_data.csv` and for anyone who already has stored entries,
because their demo history must stay open without a PIN, REQ-32) or when that
person already has an account (`detail` `this person already has an account`);
`422` when the body breaks a rule; `502` when the upstream store (Supabase) is
unreachable or returns an error.

```bash
curl -X POST "$VITE_API_BASE_URL/accounts" \
  -H "Content-Type: application/json" \
  -d '{"person_id":"demo_crew_2","pin":"2468"}'
# 201 {"person_id":"demo_crew_2"}
```

```js
const response = await fetch(`${VITE_API_BASE_URL}/accounts`, {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ person_id: "demo_crew_2", pin: "2468" }),
});
if (response.status === 409) {
  // the name is taken, or this person already has an account: sign in instead
}
```

### POST /sessions

Signs in with the same body as `POST /accounts`: `person_id` and `pin`. The
answer holds a token the frontend sends as `Authorization: Bearer <token>` on
every request that names that person.

The token is `base64url(payload) + "." + base64url(signature)`. The payload is
the JSON object `{"sub": person_id, "exp": unix_seconds}`; the signature is
`HMAC-SHA256` of the base64url payload with `SESSION_SECRET`, both base64url
without padding. It is valid for 30 days; `expires_at` is that moment in ISO
8601 UTC. When `SESSION_SECRET` is unset the API signs with a random key made at
start, so every token stops working at a restart.

Responses:

| Code | Meaning |
| --- | --- |
| `200` | `{"token": "...", "person_id": "...", "expires_at": "YYYY-MM-DDTHH:MM:SSZ"}` |
| `401` | Unknown person or wrong PIN; `detail` is `wrong username or PIN` in both cases, and an unknown person costs the same work as a wrong PIN |
| `429` | Five wrong PINs for that person inside ten minutes; `detail` is `too many wrong PINs, try again later` |
| `422` | The body breaks a rule (`person_id` not `snake_case`, `pin` not 4 to 8 digits) |
| `502` | The upstream store (Supabase) is unreachable or returns an error |

The wrong-PIN count lives in the memory of the backend process: a restart
clears it, and with more than one instance each counts its own attempts. It is
per person, so one locked astronaut does not lock another.

```bash
curl -X POST "$VITE_API_BASE_URL/sessions" \
  -H "Content-Type: application/json" \
  -d '{"person_id":"demo_astronaut_1","pin":"2468"}'
# 200 {"token":"eyJ... . ...","person_id":"demo_astronaut_1","expires_at":"2026-12-14T21:55:00Z"}
```

```js
const response = await fetch(`${VITE_API_BASE_URL}/sessions`, {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ person_id: "demo_astronaut_1", pin: "2468" }),
});
if (response.status === 429) {
  // too many wrong PINs: wait ten minutes before trying again
}
const session = await response.json(); // keep session.token and session.expires_at
```

### GET /people/{person_id}/profile

Returns one person's account settings. Today that is the mission start date,
the date Flight Day 1 is counted from: each astronaut has their own, and the
day shown is counted from it (docs/DECISIONS.md, Sat 23:08). It is stored with
the account, so any device that reads this route gets the same date.

Path parameter: `person_id` (same lowercase `snake_case` rule).

Responses:

| Code | Meaning |
| --- | --- |
| `200` | `{"person_id": "...", "mission_start": "YYYY-MM-DD"}`, or `mission_start` `null` while no date is set |
| `404` | This person has no account; `detail` is `this person has no account`. The route reads the account, it does not create one |
| `422` | `person_id` breaks the `snake_case` rule |
| `401` / `403` | As in "Sessions and the Authorization header" below |
| `502` | The upstream store (Supabase) is unreachable or returns an error |

```bash
curl "$VITE_API_BASE_URL/people/demo_crew_2/profile" \
  -H "Authorization: Bearer $TOKEN"
# 200 {"person_id":"demo_crew_2","mission_start":"2026-11-01"}
```

```js
const response = await fetch(`${VITE_API_BASE_URL}/people/${personId}/profile`, {
  headers: { Authorization: `Bearer ${session.token}` },
});
if (response.ok) {
  const profile = await response.json(); // { person_id, mission_start }
  // mission_start is null while the astronaut has not set the date: show no
  // Flight Day, and never count one from today instead
}
```

### PUT /people/{person_id}/mission_start

Sets or changes the mission start of one account (REQ-37). The date belongs to
the person, so a change here moves their Flight Day on every device that reads
it; it changes no entry and no mission day already stored.

Path parameter: `person_id` (same lowercase `snake_case` rule).

Request body:

| Field | Type | Rule |
| --- | --- | --- |
| `mission_start` | string | required; `YYYY-MM-DD`, a real calendar date, from `2000-01-01` up to tomorrow in UTC. A date further ahead is a typing mistake or a clock that is off |

The answer is the same object as `GET /people/{person_id}/profile`, with the
date the account now holds.

Responses: `200`; `404` `this person has no account` (a person without an
account has nothing to store a date on); `422` when `person_id` or
`mission_start` breaks a rule; `401` / `403` as below; `502` when the upstream
store (Supabase) is unreachable or returns an error.

```bash
curl -X PUT "$VITE_API_BASE_URL/people/demo_crew_2/mission_start" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"mission_start":"2026-11-01"}'
# 200 {"person_id":"demo_crew_2","mission_start":"2026-11-01"}
```

```js
const response = await fetch(
  `${VITE_API_BASE_URL}/people/${personId}/mission_start`,
  {
    method: "PUT",
    headers: {
      "Content-Type": "application/json",
      Authorization: `Bearer ${session.token}`,
    },
    body: JSON.stringify({ mission_start: "2026-11-01" }),
  }
);
if (response.status === 422) {
  // not a real date, before 2000-01-01, or more than a day ahead: ask again
}
const profile = await response.json(); // { person_id, mission_start }
```

### POST /entries

Stores one measurement (REQ-27) and returns the stored entry. The same entry can
be re-sent (the frontend re-sends what waits in its outbox, REQ-13) without
creating a duplicate: one entry is kept per `person_id`, `indicator_id`,
`mission_day` and `time`.

Request body: one `Entry`. Every field is required except `context`, which
defaults to `rest` when omitted.

| Field | Type | Rule |
| --- | --- | --- |
| `person_id` | string | at most 64 characters, lowercase `snake_case`: letters, digits and underscores, starts with a letter, no spaces |
| `indicator_id` | string | at most 64 characters, same rule as `person_id` |
| `value` | number | a finite number; booleans and strings are rejected |
| `unit` | string | at most 64 characters, the indicator's unit from `config/data/indicators.csv` (see below) |
| `mission_day` | integer | greater than 0, at most 100000, "day N"; booleans and strings are rejected |
| `time` | string | `HH:MM`, 24-hour clock |
| `context` | string | `rest`, `after_exercise`, `on_waking` or `before_sleep`; any other value is rejected |

The id rule is `../FORMATS.md` section 2. The example ids here are placeholders
(`demo_astronaut_1`, `example_indicator`).

When `config/data/indicators.csv` exists, the backend also checks the indicator:
an unknown `indicator_id` returns `unknown indicator`, and a `unit` that differs
from the file's unit returns `unit mismatch`. Until Phys writes that file, the
check is skipped and any id and unit are accepted.

Responses:

| Code | Meaning |
| --- | --- |
| `201` | A new entry was stored; the stored entry is returned. |
| `200` | An entry with the same `person_id`, `indicator_id`, `mission_day` and `time` already exists with the same `value`, `unit` and `context`; that stored entry is returned and nothing is added. |
| `409` | An entry with the same key already exists with a different `value`, `unit` or `context`; `detail` is a short plain message. |
| `422` | Validation (field rule, or indicator check). |

```bash
curl -X POST "$VITE_API_BASE_URL/entries" \
  -H "Content-Type: application/json" \
  -d '{"person_id":"demo_astronaut_1","indicator_id":"example_indicator","value":1.5,"unit":"example_unit","mission_day":1,"time":"13:30","context":"rest"}'
# 201 {"person_id":"demo_astronaut_1","indicator_id":"example_indicator","value":1.5,"unit":"example_unit","mission_day":1,"time":"13:30","context":"rest"}
# re-sending the same body returns 200 with the same stored entry
```

```js
const response = await fetch(`${VITE_API_BASE_URL}/entries`, {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({
    person_id: "demo_astronaut_1",
    indicator_id: "example_indicator",
    value: 1.5,
    unit: "example_unit",
    mission_day: 1,
    time: "13:30",
    context: "rest",
  }),
});
const entry = await response.json(); // status 201 (new) or 200 (already stored); the entry echoes the request
```

### GET /people/{person_id}/indicators/{indicator_id}/history

Returns one person's earlier entries for one indicator, ordered by `mission_day`
then `time`, oldest first.

Path parameters: `person_id` and `indicator_id`, strings (same lowercase
`snake_case` rule).

Responses: `200` (a JSON array of `Entry`), an empty array when there are no
entries; `422` when a path id breaks the `snake_case` rule; `502` when the
upstream store (Supabase) is unreachable or returns an error.

```bash
curl "$VITE_API_BASE_URL/people/demo_astronaut_1/indicators/example_indicator/history"
# 200 [{"person_id":"demo_astronaut_1","indicator_id":"example_indicator","value":1.5,"unit":"example_unit","mission_day":1,"time":"13:30","context":"rest"}]
```

```js
const response = await fetch(
  `${VITE_API_BASE_URL}/people/demo_astronaut_1/indicators/example_indicator/history`
);
const history = await response.json(); // array, oldest entry first
```

### GET /people/{person_id}/indicators/{indicator_id}/state

Returns one value against that person's own baseline (REQ-12, REQ-27). The
baseline is computed from the stored history, never from a file: nothing here
is a fixed range.

Path parameters: `person_id` and `indicator_id`, strings (same lowercase
`snake_case` rule).

Query parameters:

| Name | Type | Rule |
| --- | --- | --- |
| `value` | number | required; a finite number (the value the astronaut enters) |
| `context` | string | `rest` (default), `after_exercise`, `on_waking` or `before_sleep`; a reading is only compared with readings in the same context |
| `mission_day` | integer | optional; the mission day of the value being tested, greater than 0; given with `time` or not at all |
| `time` | string | optional; the `HH:MM` clock time of the value being tested; given with `mission_day` or not at all |

The rule is FORMATS.md section 3, "How each value is compared", and
`docs/findings/phys-02-baseline-state-rule.md`:

- The window is the last 14 stored entries for the person and indicator in the
  same context, oldest first. With `mission_day` and `time`, only the entries
  strictly earlier than that day and time are kept, so a reading the app has
  already stored is not compared with its own copy; without them every stored
  entry counts, as before.
- `median` is the median of the window; `spread` is
  `max(1.4826 × median absolute deviation, min_spread)`, with `min_spread` from
  that indicator's row in `config/data/indicators.csv`.
The checks run in this order (phys-02, safety decision of Sat 14 Nov):

1. A matching row of `config/rules/attention.csv` whose `source` is a link
   gives `needs_review` and the row, with or without a baseline. When several
   rows match, the most severe `notify` wins (`crew` < `cmo` <
   `flight_surgeon`). A row marked `Assumption` is ignored: it never gives
   `needs_review` and never appears in `attention`.
2. Otherwise, fewer than 3 entries gives `no_data`; `median` and `spread` are
   null and `n` counts the entries available.
3. Otherwise, a value at most 3 spreads from the median is `in_range`, and
   anything further is `outside_range`. `attention` is null.

So a core temperature of 39.5 °C on the first day, past a cited limit, is
`needs_review` and not `no_data`, while the same value past an `Assumption`
limit is `no_data`.

Four points the decision does not settle, resolved here and reported as open
questions in `team/eng1/`:

- The window counts entries, not days: entries carry a mission day and a time,
  not a date, so "the last 14 days" cannot be measured from the store.
- A row's `source` counts as a link when every word in it starts with
  `https://` or `http://`; a cell that mixes a link and `Assumption` does not.
- A value exactly on an attention threshold does not trigger that row.
- Two matching rows with the same `notify` are not defined by FORMATS.md; the
  more extreme threshold wins, as the shared vectors in
  `scripts/fixtures/format_rules/attention.json` record.

Responses: `200` (an `IndicatorState`); `404` when `indicator_id` has no row in
`config/data/indicators.csv` (also while that file does not exist, because then
no indicator is known and the noise floor cannot be read); `422` when a path id
breaks the `snake_case` rule, `value` is missing or not a finite number,
`context` is not one of the four, only one of `mission_day` and `time` is
given, or `mission_day` is not a positive integer or `time` is not `HH:MM`;
`502` when the upstream store (Supabase) is unreachable or returns an error.

| Field | Type | Meaning |
| --- | --- | --- |
| `state` | string | `no_data`, `in_range`, `outside_range` or `needs_review` |
| `median` | number or null | the window's median, in the indicator's unit |
| `spread` | number or null | the window's spread, in the indicator's unit |
| `n` | integer | how many entries the window holds |
| `attention` | object or null | the attention row that matched: `attention_level`, `notify`, `source` |

```bash
curl "$VITE_API_BASE_URL/people/demo_astronaut_1/indicators/hr_bpm/state?value=72&context=rest"
# 200 {"state":"in_range","median":70.0,"spread":4.0,"n":14,"attention":null}
```

```js
const params = new URLSearchParams({ value: "72", context: "rest" });
const response = await fetch(
  `${VITE_API_BASE_URL}/people/demo_astronaut_1/indicators/hr_bpm/state?${params}`
);
const status = await response.json();
// { state: "in_range", median: 70.0, spread: 4.0, n: 14, attention: null }
if (status.attention !== null) {
  // status.state === "needs_review": show status.attention.attention_level,
  // who is notified, and the source; the CMO or flight surgeon confirms.
}
```

The values above are placeholders in a synthetic history (REQ-14); no real crew
data and no clinical limit is stored in this endpoint.

### GET /people/{person_id}/blood_pressure/state

One blood pressure reading shows the worse of its systolic and diastolic state
(FORMATS.md section 3 and `docs/findings/bio2-01-pressure-state-rule.md`). Each
side is computed like the state route, against its own history: `systolic`
against `bp_sys_mmhg`, `diastolic` against `bp_dia_mmhg`.

Path parameter: `person_id`, a string (same lowercase `snake_case` rule).

Query parameters:

| Name | Type | Rule |
| --- | --- | --- |
| `systolic` | number | required; a finite number, in the unit of `bp_sys_mmhg` (mmHg) |
| `diastolic` | number | required; a finite number, in the unit of `bp_dia_mmhg` (mmHg) |
| `context` | string | `rest` (default), `after_exercise`, `on_waking` or `before_sleep` |
| `mission_day` | integer | optional; the mission day of the reading, greater than 0; given with `time` or not at all |
| `time` | string | optional; the `HH:MM` clock time of the reading; given with `mission_day` or not at all |

The worse state is the one furthest along `no_data` < `in_range` <
`outside_range` < `needs_review`. A reading of 120/95 is therefore
`needs_review`, because the diastolic side crossed the attention row of
`config/rules/attention.csv` while the systolic side stayed in range; 118/75 with
a usual baseline is `in_range`. When both sides need review, each side's
`attention` object carries its own level and who is notified.

`mission_day` and `time` work as they do on the state route: with both, each
window holds only the entries strictly earlier than that day and time, so the
reading being tested is not compared with a stored copy of itself.

Responses: `200` (a `BloodPressureState`); `404` when `bp_sys_mmhg` or
`bp_dia_mmhg` has no row in `config/data/indicators.csv` (also while that file
does not exist); `422` under the same rules as the state route, with `systolic`
or `diastolic` in place of `value`; `502` when the upstream store (Supabase) is
unreachable or returns an error.

| Field | Type | Meaning |
| --- | --- | --- |
| `state` | string | the worse of the two states |
| `systolic` | object | the same body the state route returns, for `bp_sys_mmhg` |
| `diastolic` | object | the same body the state route returns, for `bp_dia_mmhg` |

```bash
curl "$VITE_API_BASE_URL/people/demo_astronaut_1/blood_pressure/state?systolic=120&diastolic=95&context=rest"
# 200 {"state":"needs_review","systolic":{"state":"in_range","median":115.0,"spread":5.0,"n":14,"attention":null},"diastolic":{"state":"needs_review","median":75.0,"spread":4.0,"n":14,"attention":{"attention_level":"consult","notify":"cmo","source":"https://www.who.int/news-room/fact-sheets/detail/hypertension"}}}
```

```js
const params = new URLSearchParams({ systolic: "120", diastolic: "95", context: "rest" });
const response = await fetch(
  `${VITE_API_BASE_URL}/people/demo_astronaut_1/blood_pressure/state?${params}`
);
const pressure = await response.json();
// show both numbers and pressure.state; the source of the attention row sits
// next to it, and the CMO or flight surgeon confirms.
```

The numbers above are placeholders in a synthetic history (REQ-14); the states
come from the store, never from a fixed range in the code.
### GET /people/{person_id}/conditions

Returns the evidence score of every possible condition in
`config/rules/conditions.csv` (REQ-06), one entry per row, in file order. The
score is evidence from what the person recorded, not a probability: it says how
much of what is known points at that condition, and the CMO or the flight
surgeon confirms (`docs/findings/bio2-02-evidence-score.md`). Nothing in the
response says the person has the condition.

Path parameter: `person_id` (same lowercase `snake_case` rule).

The rule is FORMATS.md section 3, "How each value is compared", point 3:

| Question | Answer |
| --- | --- |
| Which reading is scored? | The newest stored entry of the signal. Its `context` decides what it is compared with. |
| What is its baseline? | `state.py`'s: the last 14 readings before the newest one in that same context, median and spread with the indicator's `min_spread`. |
| What does one signal add? | `1` when the value crossed a row of `config/rules/attention.csv` whose `side` is the signal's side and whose `source` is a link, with or without a baseline. Rows marked `Assumption` never add this point. `0.5` when it is outside the baseline on that side. `0` otherwise, including a value on the wrong side of the condition, whatever its distance from the baseline: a glucose of 180 mg/dL adds nothing to `hypoglycaemia`. |
| When is a signal not usable? | With no reading, no side in `based_on`, or no baseline (fewer than 3 readings in that context, or no row in `config/data/indicators.csv`) and no cited limit crossed. It is listed, with `contribution` and `value` null, and left out of the mean. |
| How is the score computed? | The mean of the usable signals, from 0 to 1, shown with three decimals. Fewer than 2 usable signals gives `score` null and `label` `no_data`, never a low score. |

Labels:

| Score | `label` | What the astronaut reads |
| --- | --- | --- |
| 0 to 0.3 | `low` | "Not likely with what you have recorded" |
| 0.3 to 0.6 | `possible` | "Possible. These signals point to it: ..." |
| 0.6 to 1 | `review` | "Ask your CMO or flight surgeon to check this" |
| null | `no_data` | "Not enough data yet", with the signals still missing |

Four points the finding does not settle, resolved here:

- The bands are written in the finding with both ends (`0 to 0.3`, `0.3 to
  0.6`, `0.6 to 1`). They are read closed at the lower end, so exactly 0.3 is
  `possible` and exactly 0.6 is `review`.
- The context is the newest reading's own: heart rate after exercise is
  compared with readings after exercise, and a context with fewer than 3
  readings leaves the signal without a baseline.
- A signal without a baseline still adds 1 when its value crossed a cited
  attention row on its side (bio2-02: "a clinical boundary does not need a
  baseline"); with no cited row crossed it is left out of the score.
- The finding's fourth vector gives a diastolic of 120 the baseline point for
  `orthostatic_intolerance`, whose diastolic signal is `below`, and reads 0.667
  `review`. With the side it adds 0, and the condition scores 0.5 `possible`.
  Open with Bio 2; the rule in words, FORMATS.md and this route agree on the
  side.

Responses: `200` (a JSON array, empty when `config/rules/conditions.csv` does
not exist); `422` when `person_id` breaks the `snake_case` rule; `502` when the
upstream store (Supabase) is unreachable or returns an error. There is no `404`:
the route does not look up an indicator.

| Field | Type | Meaning |
| --- | --- | --- |
| `condition_id` | string | the id from `config/rules/conditions.csv` |
| `name` | string | the plain name from that row |
| `score` | number or null | the mean of the usable signals, 0 to 1, three decimals |
| `label` | string | `no_data`, `low`, `possible` or `review` |
| `signals` | array | one object per signal in `based_on`, in file order |
| `source` | string | the row's link or `Assumption` |

Each signal object:

| Field | Type | Meaning |
| --- | --- | --- |
| `indicator_id` | string | the signal's indicator |
| `side` | string or null | `above` or `below`, the side that counts for this condition; null when `based_on` has no side |
| `contribution` | number or null | `1`, `0.5` or `0`, the point the signal added; null while it is not usable |
| `value` | number or null | the newest reading, or null when there is none |

```bash
curl "$VITE_API_BASE_URL/people/demo_astronaut_1/conditions"
# 200 [{"condition_id":"orthostatic_intolerance","name":"Orthostatic intolerance","score":0.5,"label":"possible","signals":[{"indicator_id":"hr_bpm","side":"above","contribution":1.0,"value":112.0},{"indicator_id":"bp_sys_mmhg","side":"below","contribution":0.5,"value":95.0},{"indicator_id":"bp_dia_mmhg","side":"below","contribution":0.0,"value":74.0}],"source":"http://humanresearchroadmap.nasa.gov/Evidence/reports/ORTHO.pdf"}]
```

```js
const response = await fetch(
  `${VITE_API_BASE_URL}/people/demo_astronaut_1/conditions`
);
const conditions = await response.json(); // one entry per condition, in file order
for (const condition of conditions) {
  if (condition.score === null) {
    // condition.label is "no_data": show the name and which signals are still
    // missing (contribution === null), never a low score
    continue;
  }
  // show condition.name, condition.label and condition.score as a bar,
  // never as a percentage; the CMO or the flight surgeon confirms
}
```

The values above are placeholders in a synthetic history (REQ-14).

### POST /people/{person_id}/pain

Stores one pain report from the 3D body (B-3): the region the astronaut
selected, the intensity from 0 to 10, the mission day and the time, with an
optional note. The intensity is kept as the astronaut set it. This route does
not read it, does not compare it with anything and adds no text about it: what
it means is for the CMO or the flight surgeon to say, not for the API.

The same report can be re-sent (the frontend re-sends what waits in its outbox,
REQ-13) without adding a second row: one report is kept per `person_id`,
`region_id`, `mission_day` and `time`.

Path parameter: `person_id`, a string (same lowercase `snake_case` rule).

Request body: one report. Every field is required except `note`.

| Field | Type | Rule |
| --- | --- | --- |
| `region_id` | string | at most 64 characters, lowercase `snake_case`: letters, digits and underscores, starts with a letter; the id from the frontend's region list. The API does not check it against a file, because `config/content/body_regions.csv` does not exist yet. |
| `intensity` | integer | 0 to 10; booleans, decimals and strings are rejected |
| `mission_day` | integer | greater than 0, at most 100000, "day N"; booleans and strings are rejected |
| `time` | string | `HH:MM`, 24-hour clock |
| `note` | string | optional, at most 280 characters |

Responses:

| Code | Meaning |
| --- | --- |
| `201` | A new report was stored; the stored report is returned, with `person_id` taken from the path and `note` null when it was not given. |
| `200` | A report with the same `person_id`, `region_id`, `mission_day` and `time` already exists with the same `intensity` and `note`; that stored report is returned and nothing is added. |
| `409` | A report with that key already exists with a different `intensity` or `note`; `detail` is a short plain message. |
| `422` | A field breaks a rule, or `person_id` in the path breaks the id rule. |
| `401` / `403` | The token rule below, when that person has an account. |
| `502` | The upstream store (Supabase) is unreachable or returns an error. |

```bash
curl -X POST "$VITE_API_BASE_URL/people/demo_astronaut_1/pain" \
  -H "Content-Type: application/json" \
  -d '{"region_id":"left_knee","intensity":4,"mission_day":1,"time":"13:30","note":"After the treadmill run"}'
# 201 {"region_id":"left_knee","intensity":4,"mission_day":1,"time":"13:30","note":"After the treadmill run","person_id":"demo_astronaut_1"}
# re-sending the same body returns 200 with the same stored report
```

```js
const response = await fetch(
  `${VITE_API_BASE_URL}/people/demo_astronaut_1/pain`,
  {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      Authorization: `Bearer ${session.token}`, // only when that person has an account
    },
    body: JSON.stringify({
      region_id: "left_knee",
      intensity: 4,
      mission_day: 1,
      time: "13:30",
      note: "After the treadmill run",
    }),
  }
);
if (response.status === 201 || response.status === 200) {
  // stored: the report waits no more in the outbox
}
if (response.status === 409) {
  // this person, region, day and time already hold another report: do not
  // retry, ask the astronaut which one is right
}
const report = await response.json(); // {"region_id":"left_knee","intensity":4,"mission_day":1,"time":"13:30","note":"After the treadmill run","person_id":"demo_astronaut_1"}
```

### GET /people/{person_id}/pain

Returns one person's pain reports, ordered by `mission_day` then `time`, oldest
first. A person with no report gets an empty array, never a `404`: the route
does not look the person up.

Path parameter: `person_id` (same lowercase `snake_case` rule).

Query parameters:

| Name | Type | Rule |
| --- | --- | --- |
| `region_id` | string | optional; only the reports of that region, same id rule as in the body. An id with no report gives an empty array. |

Each object has the fields of the body above plus `person_id`. The API does not
add a state, a threshold or a text about the intensity.

Responses: `200` (a JSON array, empty when there is no report); `422` when
`person_id` or `region_id` breaks the `snake_case` rule; `401` / `403` as below
when that person has an account; `502` when the upstream store (Supabase) is
unreachable or returns an error.

```bash
curl "$VITE_API_BASE_URL/people/demo_astronaut_1/pain?region_id=left_knee"
# 200 [{"region_id":"left_knee","intensity":4,"mission_day":1,"time":"13:30","note":"After the treadmill run","person_id":"demo_astronaut_1"}]
```

```js
const params = new URLSearchParams({ region_id: "left_knee" });
const response = await fetch(
  `${VITE_API_BASE_URL}/people/demo_astronaut_1/pain?${params}`
);
const reports = await response.json(); // array, oldest report first
for (const report of reports) {
  // show report.region_id on the 3D body and report.intensity as the number
  // the astronaut chose; nothing else is attached to it
}
```

The reports above are in a synthetic history (REQ-14); no real crew data is
stored in this endpoint.

## Sessions and the Authorization header

Every route that names a person checks who is asking before it answers:

| Route | Whose person |
| --- | --- |
| `POST /entries` | `person_id` in the body |
| `GET /people/{person_id}/indicators/{indicator_id}/history` | the path |
| `GET /people/{person_id}/indicators/{indicator_id}/state` | the path |
| `GET /people/{person_id}/blood_pressure/state` | the path |
| `GET /people/{person_id}/conditions` | the path |
| `POST /people/{person_id}/pain` | the path |
| `GET /people/{person_id}/pain` | the path |
| `GET /people/{person_id}/profile` | the path |
| `PUT /people/{person_id}/mission_start` | the path |

The rule depends on whether that person has an account:

- A person **with** an account needs `Authorization: Bearer <token>`, a token
  from `POST /sessions` for that same person.
  - No header, or a value that is not `Bearer <token>`: `401`, `detail`
    `missing or invalid token`.
  - A token that was tampered with, signed with another key or past its
    `expires_at`: `401`, same `detail`.
  - A valid token for another person: `403`, `detail` `this token belongs to
    another person`.
- A person **without** an account stays open, as every route was before
  accounts existed: the synthetic demo astronaut and the smoke-test person keep
  working without a token (REQ-32). Nothing else about their requests changes.

`GET /health`, `POST /accounts` and `POST /sessions` never need a token.

The check runs before the route's own work: a refused request reads no history
and stores no entry.

```bash
TOKEN="eyJ..."
curl "$VITE_API_BASE_URL/people/demo_astronaut_1/indicators/hr_bpm/history" \
  -H "Authorization: Bearer $TOKEN"
# 200 [...]  without the header: 401 {"detail":"missing or invalid token"}
```

```js
const response = await fetch(
  `${VITE_API_BASE_URL}/people/demo_astronaut_1/indicators/hr_bpm/history`,
  { headers: { Authorization: `Bearer ${session.token}` } }
);
if (response.status === 401) {
  // no token, a tampered one or an expired one: sign in again with the PIN
}
if (response.status === 403) {
  // the token belongs to another person: ask for that person's PIN
}
```

## Errors

`POST /entries` returns `422` in two cases.

Field validation: `detail` is an array with one object per error; `msg` holds the
message.

| Cause | `msg` |
| --- | --- |
| `mission_day` is 0 or negative | `Input should be greater than 0` |
| `mission_day` is above 100000 | `Input should be less than or equal to 100000` |
| `person_id`, `indicator_id` or `unit` is longer than 64 characters | `String should have at most 64 characters` |
| `value` is a boolean or a string | `Input should be a valid number` |
| `mission_day` is a boolean or a string | `Input should be a valid integer` |
| `time` is not `HH:MM` 24-hour | `Value error, time must be HH:MM (24-hour)` |
| `person_id` or `indicator_id` breaks the id rule | `Value error, must be lowercase snake_case` |
| a field is missing | `Field required` |

Indicator check: `detail` is a plain string.

| Cause | `detail` |
| --- | --- |
| `indicator_id` not in `config/data/indicators.csv` | `unknown indicator` |
| `unit` differs from the file's unit | `unit mismatch` |

`POST /entries` returns `409` when an entry with the same `person_id`,
`indicator_id`, `mission_day` and `time` already exists with a different
`value`, `unit` or `context`. The `detail` is the plain string `an entry for
this person, indicator, day and time already exists with a different value`.

`GET /people/{person_id}/indicators/{indicator_id}/history` returns `422` with a
plain-string `detail` when `person_id` or `indicator_id` breaks the `snake_case`
rule, and `502` with `detail` `upstream storage error` when the Supabase store
is unreachable or returns an error.

`GET /people/{person_id}/conditions` returns `422` with the plain-string
`detail` `person_id must be lowercase snake_case`, and the same `502` with the
same `detail` as the routes above.

`POST /people/{person_id}/pain` returns `422` with the field array when the body
breaks a rule:

| Cause | `msg` |
| --- | --- |
| `intensity` is below 0 or above 10 | `Input should be greater than or equal to 0` / `Input should be less than or equal to 10` |
| `intensity` is a boolean, a decimal or a string | `Input should be a valid integer` |
| `mission_day` is 0 or negative, or above 100000 | `Input should be greater than 0` / `Input should be less than or equal to 100000` |
| `region_id` is longer than 64 characters | `String should have at most 64 characters` |
| `note` is longer than 280 characters | `String should have at most 280 characters` |
| `region_id` breaks the id rule | `Value error, must be lowercase snake_case` |
| `time` is not `HH:MM` 24-hour | `Value error, time must be HH:MM (24-hour)` |
| a field is missing | `Field required` |

It returns `409` with the plain string `a pain report for this person, region,
day and time already exists with a different intensity or note` when that key
already holds another report. Both pain routes return `422` with a plain-string
`detail` when `person_id`, or the `region_id` filter, breaks the `snake_case`
rule, and the same `502` as the routes above.

`POST /accounts`, `POST /sessions` and `PUT /people/{person_id}/mission_start`
return `422` with the field array when the body breaks a rule:

| Cause | `msg` |
| --- | --- |
| `person_id` breaks the id rule | `Value error, must be lowercase snake_case` |
| `pin` is not 4 to 8 digits | `Value error, pin must be 4 to 8 digits` |
| `person_id` or `pin` is missing | `Field required` |
| `mission_start` is not `YYYY-MM-DD` | `Value error, mission_start must be YYYY-MM-DD` |
| `mission_start` is not a real calendar date (month 13, 30 February) | `Value error, mission_start must be a real calendar date` |
| `mission_start` is before 2000-01-01 | `Value error, mission_start must be 2000-01-01 or later` |
| `mission_start` is more than a day ahead | `Value error, mission_start cannot be more than one day ahead` |
| `mission_start` is missing on the `PUT` | `Field required` |

`POST /accounts` returns `409` with `detail` `this username is taken` when the
name belongs to the demo data, the smoke test or a person with stored entries,
and with `detail` `this person already has an account` when the account exists.
`POST /sessions` returns `401` with `detail` `wrong username or PIN`
and `429` with `detail` `too many wrong PINs, try again later`.

The nine routes that name a person return `401` with `detail` `missing or
invalid token` and `403` with `detail` `this token belongs to another person`;
both come from the rule above, before the route does its own work. The two that
read or write account settings, `GET /people/{person_id}/profile` and
`PUT /people/{person_id}/mission_start`, also return `404` with `detail`
`this person has no account` when the person has none.

## CORS

The backend reads `ALLOWED_ORIGINS`, a comma-separated list of origins. When it
is unset or empty, the default is `http://localhost:5173` (the Vite dev server).
Allowed methods are `GET`, `POST` and `PUT`; allowed headers are `Content-Type`
and `Authorization`, so the frontend can send the bearer token. A preflight
`OPTIONS` request returns `200` with `access-control-allow-origin` set to the
allowed origin.

## Rate limit

Every client address is capped at 120 requests per 60 seconds
(`backend/app/ratelimit.py`), sign-in included; the per-person PIN lockout in
`POST /sessions` is a second, separate guard. The window slides: a request is
accepted while that address made fewer than 120 requests in the last 60
seconds.

- `RATE_LIMIT_PER_MINUTE` sets the cap; unset or empty means 120 and `0` turns
  the limit off. A value that is not a whole number, or is negative, is read as
  120.
- The address is the last value of `X-Forwarded-For` when the header is
  present, else the socket address. The deployed API sits behind Railway's
  proxy, so the socket address of every request is the proxy. The proxy appends
  the address it saw to the end of that header; earlier values come from the
  client and can be forged, so they are not used.
- `GET /health`, `GET /docs` (and `/docs/oauth2-redirect`) and
  `GET /openapi.json` are exempt: they are never counted and never refused, so
  the health check and the schema stay reachable.
- Over the cap the answer is `429`, with `Retry-After` holding the seconds
  until the oldest request in the window leaves it, and this body:

```json
{"detail": "too many requests, try again in a minute"}
```

```js
const response = await fetch(`${VITE_API_BASE_URL}/health`);
if (response.status === 429) {
  const wait = Number(response.headers.get("Retry-After")); // seconds
  // wait before sending again; the entry stays in the outbox meanwhile (REQ-13)
}
```

Every route counts, `POST /entries` included. The counter lives in the memory of
the backend process: with more than one instance each counts its own requests,
and a restart clears every window.

## Not in the API yet

- No endpoint lists people.
- No endpoint lists indicators.
- No change of PIN, no sign-out and no refresh of a token: a token works until
  `expires_at`.
- No update or delete of entries or pain reports.

These are facts about the current code, not proposals.
